# 장시간 운영 검증 준비

현재는 실행 계획과 기존 증거를 정리한 단계다. 새 장시간 관측·Paper 재개·자동 재시작을 시작하거나 예약하지 않았다. 기존 미국 2026-11-03 23:35 KST 일회성 실행은 그대로 유지한다. 실제 주문은 대상에 포함하지 않는다.

## 검증을 분리하는 이유

| 항목                  | 이미 확인한 증거                                                | 다음에 필요한 증거                                          |
| --------------------- | --------------------------------------------------------------- | ----------------------------------------------------------- |
| 정규장 데이터 수집    | KR/US 각각 60/60 healthy, 오류·차단·공백 0인 별도 구간          | 개장·마감·거래일 경계의 실제 기록                           |
| 읽기 전용 source 수명 | 진행 중 요청 취소 → 요청 정리 → 잠금 해제 → 새 연결 1회         | 실제 OS 프로세스 정상 종료와 별도 프로세스 시작의 연결 증거 |
| 토큰 갱신             | 가짜 시계/fetch의 동시 발급 억제·만료 전 갱신·401 후 1회 재발급 | 실제 응답의 유효기간을 넘긴 동일 소유자의 갱신 증거         |
| Paper 수명            | 합성 DB의 부분 체결·재시작·중복 방지·기본 정지                  | 실제 시세에서의 장시간 운영과 체결 경로                     |

서로 다른 실행의 샘플 수나 소요 시간을 합산해 장시간 연속 실행으로 채택하지 않는다. PID 생존, PC가 켜진 시간, 리포트 `completed`, 일회성 재연결 성공만으로 토큰 갱신을 입증하지 않는다. 상세 근거는 [운영 검증 기록](OPERATIONAL_VALIDATION.md)을 따른다.

## 실제 프로세스 수명 검증 순서

1. 기존 broker 소유자와 공유 연결을 확인하고, 미국 예약 실행과 자원/시간이 겹치지 않는 별도 유한 검증 구간을 정한다. 같은 client·잠금 DB를 유지한다. 소유권 경합을 새 토큰 발급으로 우회하지 않는다.
2. 실행 전 source·종목·빌드·횟수·간격·종료 기한을 고정하고 서버 전용 증거 디렉터리를 만든다. 실제 Paper 계좌의 설정·정지 상태·원장을 읽기 전용으로 보관한다. 조회용 종목을 전략·관심종목 변경으로 확대하지 않는다.
3. 기존 `market-observation-run`을 **별도 자식 프로세스**로 실행하고, 저장된 첫 관측 증거가 생긴 뒤 해당 자식에만 SIGTERM을 보낸다. 웹/API/DB/Docker/다른 관측 프로세스는 종료하지 않는다.
4. 자식 종료와 terminal/journal 검증, 공유 요청 정리·IPC 정리·같은 DB/client 잠금 해제를 확인한다. 취소된 리포트를 healthy 완료로 바꾸지 않는다. 기다림에도 기한을 둔다. 강제 종료가 필요하면 정상 정리 통과로 처리하지 않는다.
5. 앞 소유자가 정리된 다음, **다른 자식 프로세스**로 1회 읽기 전용 관측을 수행한다. 새 token manager의 시작과 새 인스턴스 연결은 토큰 만료 갱신과 구분한다. 결과·잠금 정리·Paper 원장 보존을 확인한다. 실패 시 자동 재시도/재예약하지 않는다.

기존 프로세스 내 source 취소 증거와 새 OS 프로세스 종료/기동 증거를 구분해 저장해야 한다. 이미 승인된 미국 Paper 실행을 재시작 실험 대상으로 사용하지 않는다.

## 실제 토큰 수명 검증 준비

구현된 transport는 `expires_in`과 발급 시각으로 갱신 시각을 정한다. 실제 TTL을 예시 값 86,400초로 고정하거나 테스트를 빨리 끝내려고 시계·인증키·허용 IP를 바꾸지 않는다. 새 토큰이 이전 토큰을 무효화하는 제약 때문에 다른 client 소유자를 병렬로 시작해서도 안 된다.

현재 일반 관측 리포트에는 **토큰 발급·갱신 횟수의 안전한 증거가 없다**. 긴 관측만 실행하는 것으로 갱신 검증이 끝나지 않는다. 실제 장시간 실행 전에 transport 내부에서 키/토큰/계좌 없이 발급·갱신의 횟수와 시각만 구분하는 관측 가능성을 먼저 설계·테스트해야 한다. 발급 실패는 성공 갱신으로 세지 않고, 401 재발급과 TTL 갱신도 구분한다. 이 준비 문서가 해당 계측의 구현 완료를 뜻하지 않는다.

그 다음 실제 반환 TTL과 호출 예산을 기준으로 관측 기간/간격/최대 횟수/종료 기한을 정한다. 현재 관측 CLI의 범위는 samples 1~10,000, interval-seconds 10~3,600이며 완료 후 간격을 두므로 실행 시간이 단순 곱과 같지 않다. 정규장 수집 예산을 제한하는 `--regular-only`로 여러 거래일에 걸친 연속 운용이 자동 허용된다고 해석하지 않는다. 장외 데이터의 stale/시장 차단은 기록하고 주문 승인으로 쓰지 않는다.

## 검증 기록과 종료 조건

- 토큰·인증 헤더·계좌 응답·원본 예외·PID/경로를 HTTP나 Git 문서에 복사하지 않는다. 운영용 PID와 경로는 private 서버 기록으로만 관리한다.
- 종료 요약/해시/샘플 순서/지연/공백/허용 오류 코드와 잠금·정리 증거를 검토한다. 절전/프로세스 중단 후 기록이 없으면 미확인으로 남긴다.
- Paper checkpoint의 조회 시각을 제외한 내용이 같은지 확인한다. 검증으로 Paper를 재개하거나 손실 기준을 초기화하지 않는다.
- 실제 과정이 발생하지 않은 항목은 미검증으로 남긴다. 장시간 관측 성공이 전략 수익성·Paper 체결·실거래 전환 승인은 아니다.

다음 구현 단위는 **비밀정보 없는 토큰 수명 계측**과 **별도 자식 프로세스 종료/재기동 검증기**다. 기존 transport/관측 정책 안에서 설계하고 가짜 broker부터 검사한다. 실제 장시간 실행은 그 후 고정된 유한 계획으로 진행한다.
