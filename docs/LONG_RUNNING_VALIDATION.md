# 장시간 운영 검증 준비

현재는 계측·프로세스 검증 도구와 짧은 실제 연결 검증, 무접속 유한 계획 계산까지 완료한 단계다. 새 장시간 관측은 시작하거나 예약하지 않았다. 기준 시각은 2026-11-05 18:06 KST다. 미국 Paper 일회성 실행 `e3c96a51-7ef8-46dc-b533-215cd38e7298`의 11/6 00:05~00:30 KST 예약은 고정 빌드에서 유지하며 변경·취소·재시작하지 않는다. 실제 주문은 대상에 포함하지 않는다.

## 검증을 분리하는 이유

| 항목                  | 이미 확인한 증거                                                | 다음에 필요한 증거                                          |
| --------------------- | --------------------------------------------------------------- | ----------------------------------------------------------- |
| 정규장 데이터 수집    | KR/US 각각 60/60 healthy, 오류·차단·공백 0인 별도 구간          | 개장·마감·거래일 경계의 실제 기록                           |
| 읽기 전용 source 수명 | 진행 중 요청 취소 → 요청 정리 → 잠금 해제 → 새 연결 1회         | 별도 프로세스 검증 완료; 장시간 운용 중 같은 정리 경로 확인 |
| 토큰 갱신             | 가짜 시계/fetch의 동시 발급 억제·만료 전 갱신·401 후 1회 재발급 | 실제 응답의 유효기간을 넘긴 동일 소유자의 갱신 증거         |
| Paper 수명            | 합성 DB의 부분 체결·재시작·중복 방지·기본 정지                  | 실제 시세에서의 장시간 운영과 체결 경로                     |

서로 다른 실행의 샘플 수나 소요 시간을 합산해 장시간 연속 실행으로 채택하지 않는다. PID 생존, PC가 켜진 시간, 리포트 `completed`, 일회성 재연결 성공만으로 토큰 갱신을 입증하지 않는다. 상세 근거는 [운영 검증 기록](OPERATIONAL_VALIDATION.md)을 따른다.

## 실제 프로세스 수명 검증 순서

1. 기존 broker 소유자와 공유 연결을 확인하고, 미국 예약 실행과 자원/시간이 겹치지 않는 별도 유한 검증 구간을 정한다. 같은 client·잠금 DB를 유지한다. 소유권 경합을 새 토큰 발급으로 우회하지 않는다.
2. 실행 전 source·종목·빌드·횟수·간격·종료 기한을 고정하고 서버 전용 증거 디렉터리를 만든다. 실제 Paper 계좌의 설정·정지 상태·원장을 읽기 전용으로 보관한다. 조회용 종목을 전략·관심종목 변경으로 확대하지 않는다.
3. 기존 `market-observation-run`을 **별도 자식 프로세스**로 실행하고, 저장된 첫 관측 증거가 생긴 뒤 해당 자식에만 SIGTERM을 보낸다. 웹/API/DB/Docker/다른 관측 프로세스는 종료하지 않는다.
4. 자식 종료와 terminal/journal 검증, 공유 요청 정리·IPC 정리·같은 DB/client 잠금 해제를 확인한다. 취소된 리포트를 healthy 완료로 바꾸지 않는다. 기다림에도 기한을 둔다. 강제 종료가 필요하면 정상 정리 통과로 처리하지 않는다.
5. 앞 소유자가 정리된 다음, **다른 자식 프로세스**로 1회 읽기 전용 관측을 수행한다. 새 token manager의 시작과 새 인스턴스 연결은 토큰 만료 갱신과 구분한다. 결과·잠금 정리·Paper 원장 보존을 확인한다. 실패 시 자동 재시도/재예약하지 않는다.

기존 프로세스 내 source 취소 증거와 새 OS 프로세스 종료/기동 증거를 구분해 저장해야 한다. 이미 승인된 미국 Paper 실행을 재시작 실험 대상으로 사용하지 않는다.

## 실제 토큰 수명 검증 준비

구현된 transport는 `expires_in`과 발급 시각으로 갱신 시각을 정한다. 실제 TTL을 예시 값 86,400초로 고정하거나 테스트를 빨리 끝내려고 시계·인증키·허용 IP를 바꾸지 않는다. 새 토큰이 이전 토큰을 무효화하는 제약 때문에 다른 client 소유자를 병렬로 시작해서도 안 된다.

[토큰 수명 계측](TOKEN_LIFECYCLE.md)을 구현했다. 새 관측의 명시적 `--token-lifecycle` 옵션으로만 별도 private 파일을 보관하고, 최초 발급·유효기간 갱신·401 재발급의 성공/실패/취소를 구분한다. 기존 일반 관측 리포트와 과거/고정 빌드에는 이 증거가 없으며 사후 생성하지 않는다. 구현과 가짜 API 검증이 실제 만료/갱신 검증 완료를 뜻하지 않는다. 긴 관측만 실행하거나 계측 파일의 initial 성공만으로 갱신 검증을 끝내지 않는다.

그 다음 실제 반환 TTL과 호출 예산을 기준으로 관측 기간/간격/최대 횟수/종료 기한을 정한다. 현재 관측 CLI의 범위는 samples 1~10,000, interval-seconds 10~3,600이며 완료 후 간격을 두므로 실행 시간이 단순 곱과 같지 않다. 정규장 수집 예산을 제한하는 `--regular-only`로 여러 거래일에 걸친 연속 운용이 자동 허용된다고 해석하지 않는다. 장외 데이터의 stale/시장 차단은 기록하고 주문 승인으로 쓰지 않는다.

## 무접속 계획 도구

`corepack pnpm readonly:validation:plan`은 기본 사용법 미리보기다. 옵션을 지정하면 순수 함수가 시간 예산·샘플 수·주어진 예약과의 겹침을 계산한다. 환경파일·키·DB·네트워크·자식 프로세스에 접근하거나 파일을 생성하지 않는다. 기존 Zod만 사용하며 새 의존성은 없다. 모듈 실행에 필요한 코드 파일 로딩은 일반 CLI와 같다.

```bash
# 미국 11/5 거래일 정규장 종료 전후: 11/6 05:55~06:10 KST
corepack pnpm readonly:validation:plan --kind=session \
  --start-at=2026-11-05T20:55:00Z --boundary-at=2026-11-05T21:00:00Z \
  --deadline=2026-11-05T21:10:00Z --interval-seconds=30 \
  --reserved-start=2026-11-05T15:05:00Z --reserved-end=2026-11-05T15:30:00Z

# 두 세션 후보 뒤 자연 갱신 후보: 11/6 09:15~11/7 10:30 KST
# CLI 한 구간 제한 때문에 Paper+US/KR 후보 전체를 감싸는 보수적 제외 구간 사용
corepack pnpm readonly:validation:plan --kind=expiry \
  --start-at=2026-11-06T00:15:00Z --deadline=2026-11-07T01:30:00Z \
  --interval-seconds=300 --ttl-seconds=86399 \
  --reserved-start=2026-11-05T15:05:00Z --reserved-end=2026-11-06T00:10:00Z
```

위 입력은 11/5에 다시 계산한 **미실행 후보**다. US 11/5 거래일의 정규장 종료는 hash 검증한 11/4 공식 저장 증거와 일치하지만 최신 캘린더를 이번 작업에서 조회한 것은 아니다. KR 11/6 09:00 개장은 최신 공식 증거가 아직 확인되지 않은 조건부 입력이다. TTL 86,399초 역시 11/4 실제 조회의 과거 값이며 미래 토큰에 보장되지 않는다. 실행 직전에 공식 캘린더와 전체 예약을 다시 확인해야 한다. 세션 계획은 경계 전 최소 한 간격, 경계 후 5분을 포함한다. 토큰 계획은 입력 TTL에 2분 여유를 더한 샘플 구간을 요구한다. 두 후보를 함께 실행할 경우 앞 관측의 정상 종료·잠금 정리가 확인돼야 뒤 관측을 시작할 수 있다.

| 후보             | 샘플 수 | 완료 후 간격 | 계획 예산        | 명시한 종료 기한 |
| ---------------- | ------- | ------------ | ---------------- | ---------------- |
| 정규장 종료 경계 | 21      | 30초         | 15분             | 11/6 06:10 KST   |
| 자연 토큰 갱신   | 290     | 300초        | 24시간 54분 50초 | 11/7 10:30 KST   |

예산은 `(samples−1)×interval + samples×10초 + 시작 여유 30초 + 정리 여유 60초`다. 각 관측 완료 후 대기하는 기존 동작을 반영한다. 정리/OS 정지/네트워크가 반드시 이 시간 안에 끝난다는 보장은 아니다. 단일 종목·시장·캔들 1페이지 기준 source 메서드 호출은 각각 105회/1,450회로 계산한다. HTTP 요청 수는 재시도·인증·adapter 내부 요청·공유 대시보드 요청에 따라 달라지므로 API 호출 한도 충족으로 해석하지 않는다. 기존 transport의 limiter/재시도 상한을 유지한다.

계획 창은 최대 36시간, 샘플은 최대 10,000회다. 예산 부족이나 예약 겹침은 `state=blocked`/exit 2이며 잘못된 입력은 안전한 코드/exit 1로 끝난다. 순수 함수는 최대 100개 예약 구간, CLI는 한 구간을 명시적으로 받는다. 예약 목록을 자동 조회하지 않으므로 입력하지 않은 예약·외부 프로그램은 검사하지 못한다. `prepared`는 산술 검사 결과이며 실제 시작 가능·예약·운용 승인이 아니다. 모든 출력은 `scheduled=false`, `executionEnabled=false`, `canResume=false`다.

현재 `market:observe`의 `--start-at`은 regular-only와만 조합되며 전체 절차의 절대 종료 기한을 강제하지 않는다. 따라서 위 계획을 그대로 실행 명령으로 바꾸지 않는다. [유한 관측 감독기](READONLY_SUPERVISOR.md)를 별도로 구현했다. 절대 시각 대기·시작 누락 거부·동일 broker 잠금·소유 자식의 정상 종료/정리·강제 종료의 실패 처리·계획과 빌드 hash 검증을 연결한다. 이 도구는 `requiresDeadlineSupervisor=true`로 별도 감독기를 요구함을 표시한다. 만료 갱신 관측은 하루 이상 같은 client 잠금을 점유하므로 그 구간의 다른 Paper/관측 예약을 따로 배제하고 투자 현황은 소유자의 공유 IPC를 사용해야 한다.

## 11월 5일 후보 재계산과 현재 차단

현재 묶음은 [세션·토큰 후보 상세](OBSERVATION_VALIDATION_BATCH.md)에 기록했다. US 마감·KR 개장·자연 만료 세 입력을 각각 planner와 감독기 미리보기로 실행해 총 6회 exit 0을 확인했고, Paper와 겹치는 별도 반례 1회는 `RESERVED_WINDOW_OVERLAP`/exit 2였다. 모두 키 없는 CLI이며 빌드·fingerprint·실행·예약·DB·broker·토큰 접근은 하지 않았다. 기존 Paper request 파일의 전후 바이트 SHA-256도 같았다. 프로세스 생존·원장 보존을 이번에 검사한 것은 아니다.

새 private 후보는 `.local-data/readonly-validation-batches/8b8e812e-1a1b-4d19-8d9b-4d81c1becc02/plan.json`이다. 입력 argv, 실제 출력, 소스/기존 dist의 파일 hash, 캘린더 증거 hash를 포함한다. 내용 hash는 `ba8d0dabe1e7635e49d42f914b2f6184d2ba36c5d83ee20ea89c5f4569c6cf96`이다. 이 파일은 후보 자료이며 실행 요청·종료 기록 형식을 대신하지 않는다.

과거 `a4072920-6191-48e9-bc0e-76def63dd4a0`의 request 없는 결과는 계속 미확인 차단 사유다. 감독기 미리보기는 시간·빌드·저장 예약 검사 전에 반환하므로 `prepared`/planHash를 실행 가능 판정으로 읽지 않는다. 예약 예외를 만들거나 closure를 추정 생성하지 않는다. 적법한 독립 종료 증거로 차단이 해소되지 않으면 실제 실행은 진행할 수 없다. 이 작업에서는 감사/상태를 재실행하거나 기존 증거를 변경하지 않았다.

만료 후보의 예산 종료는 11/7 10:09:50 KST, 절대 기한은 10:30이다. 앞 두 세션 후보 정상 종료·잠금 해제 후에만 검토 가능하며, 앞으로 생길 Paper 예약도 이 25시간 15분 창 전체와 다시 비교해야 한다. 시각만 늦춰 놓았다는 이유로 동시 점유·실제 TTL·최신 거래일 검증이 완료되지 않는다.

## 후속 공식 캘린더 증거 확인 — 11월 5일 18:10 KST

main이 같은 broker 잠금 소유자로 수집한 [별도 공식 캘린더 증거](../.local-data/research-expansion/d51b4d49-0528-40eb-bb5b-54a36a69c7e2/calendar-evidence.json)를 파일 읽기로 검증했다. 기록 시각은 `2026-11-05T09:10:31.363Z`다. 수집 코드의 `contentHash(calendars)` 방식에 따라 `calendars` 배열의 canonical JSON SHA-256을 재계산해 전달받은 `adc1f46afb25e3a019836a13ba6af6c1fb022f8f571db29c1ce7bb39a866a4a3` 및 파일의 `hash`와 일치함을 확인했다. 이 값은 파일 전체 바이트 hash가 아니며, 파일 바이트 SHA-256은 별도로 `2d27097bdf906076c2eba834ed3049a410be728cea964e7fac1aaeffc3717ffa`다.

`sessionsKnown=true`인 US 11/5 정규장 `2026-11-05T14:30:00Z~21:00:00Z`, KR 11/6 정규장 `2026-11-06T00:00:00Z~06:30:00Z`를 확인했다. 따라서 후보의 US 마감 11/6 06:00 KST와 KR 개장 11/6 09:00 KST는 이 후속 공식 증거와 일치한다. 앞서 기록한 KR 최신 미확인은 최초 후보 생성 당시의 상태이며, 이 절은 이후 확인 사실을 별도로 추가한 것이다.

기존 후보 `8b8e812e-1a1b-4d19-8d9b-4d81c1becc02`의 파일 바이트 SHA-256은 여전히 `8dfa24f366c9efb5a0c04f5219cbd2a3e43a208347699bc079016e5ee2baf0dc`로 같고 내용/planHash를 수정하지 않았다. 이 후속 증거는 원본 후보 hash에 포함되지 않는다. 캘린더 일치는 실제 세션 관측·TTL 갱신·원장 보존·실행 가능 판정이 아니다. a407 미확인 차단과 e3c96a51 고정 Paper 예약을 유지하며, 향후 실행 직전 최신 캘린더/전체 예약 재검토도 필요하다. 이번 확인은 API·DB 호출이나 실행·예약 없이 수행했다.

## 경계별 통과에 필요한 실제 증거

| 검증           | 필요한 증거                                                                                             | 부족하면 남길 판정                                               |
| -------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 세션 경계      | 최신 공식 캘린더, 경계 양쪽 실제 관측 시각·세션 상태, final/journal hash·순서·공백 검사                 | 경계 전/후 자료 없음, stale·오류·절전 공백은 별도 미검증/차단    |
| 자연 토큰 갱신 | 같은 transport의 initial 성공과 실제 refreshAt, expiry 성공, 그 뒤 성공한 읽기 관측, 정리 후 inFlight 0 | initial만 있음·401 재발급만 있음·후속 읽기 없음은 갱신 미검증    |
| 수명/정리      | 정리 완료와 terminal/token 파일의 연결 검증, 같은 client 잠금 해제 확인, Paper 원장 전후 보존           | PID 생존·completed 표기만으로 정리나 원장 보존을 통과시키지 않음 |

이 계획은 세션 경계와 갱신을 강제로 만들지 않는다. 실제 토큰 TTL이 예산을 넘어가면 자동 연장하지 않고 미검증으로 종료해야 한다. 새 토큰 발급·시계 변경·재기동으로 자연 갱신을 대체하지 않는다. 정규장 종료 후의 closed/blocked와 수집 오류를 분리하고 모든 표본이 healthy여야 한다는 조건을 경계 검증에 잘못 적용하지 않는다.

과거 11월 4일 두 후보 계산본은 `.local-data/readonly-validation-plans/41f01136-0ea3-4996-985c-4cd03e6490da/plan.json`에 새 생성했다. 원래 캘린더 증거 hash·계산기 소스 hash·계획 내용 hash를 보관했고, 토큰 계획에는 Paper 예약뿐 아니라 앞 세션 관측 후보의 기한도 충돌 입력으로 포함했다. 실행·예약은 하지 않았다.

다음은 11월 4일 구현 당시의 검증 이력이며 이번 문서 작업의 검사 수가 아니다. 당시 새 테스트 5개는 TTL별 계산·경계 전후·완료 후 간격·예약 포함/부분 겹침·기한 부족·유효하지 않은 입력·무접속 CLI/실행 옵션 거부를 확인했다. 전체 기본 검사에서 470개가 통과했고, 샌드박스의 로컬 소켓 생성 제한으로 실패한 기존 IPC 파일을 권한 환경에서 재실행해 8개 모두 통과했다(기본 검사 통과분과 3개 중복). 따라서 기본 테스트 475개가 검증됐으며 DB 통합 102개는 기본 실행에서 제외됐다. 타입·린트·전체 빌드·포맷 검사도 통과했다. 테스트는 실제 broker API를 호출하지 않았다.

## 검증 기록과 종료 조건

- 토큰·인증 헤더·계좌 응답·원본 예외·PID/경로를 HTTP나 Git 문서에 복사하지 않는다. 운영용 PID와 경로는 private 서버 기록으로만 관리한다.
- 종료 요약/해시/샘플 순서/지연/공백/허용 오류 코드와 잠금·정리 증거를 검토한다. 절전/프로세스 중단 후 기록이 없으면 미확인으로 남긴다.
- Paper checkpoint의 조회 시각을 제외한 내용이 같은지 확인한다. 검증으로 Paper를 재개하거나 손실 기준을 초기화하지 않는다.
- 실제 과정이 발생하지 않은 항목은 미검증으로 남긴다. 장시간 관측 성공이 전략 수익성·Paper 체결·실거래 전환 승인은 아니다.

[별도 자식 프로세스 검증기](READONLY_PROCESS_CHECK.md)도 구현하고 실제 읽기 전용 SIGTERM 종료/새 프로세스 1회 연결을 확인했다. 준비 Paper 두 계좌는 별도 checkpoint 비교에서 보존됐다. 이는 국내 정규장 밖의 짧은 연결 검증이며 다음은 실제 TTL/호출 예산을 반영한 유한 관측 계획이다. 기존 미국 예약을 실험 대상으로 사용하지 않았고 실제 장시간 실행도 자동 시작하지 않았다.
