# Paper 전략 설정과 활성 관리

## 저장과 실행

Paper 페이지에서 기존 등록 전략의 종목·단기/장기 이동평균 기간·주문 수량·관측당 최대 체결 수량·등록 활성 상태를 편집한다. 저장은 소유자 로그인과 localhost 경계를 요구한다. 브라우저는 계좌나 구현 버전을 지정하지 않는다. 새 전략 등록/삭제·구현 교체·한도 편집·worker 시작/재개는 UI에 추가하지 않았다.

현재 definition은 moving-average-cross와 KR/US 종목, 검증된 정수 기간/수량만 허용한다. 단기 < 장기, 최대 체결 수량 ≤ 주문 수량을 요구한다. 현재 합성 CLI source는 KR만 지원하므로 UI의 US 선택은 비활성이다. 다른 전략 플러그인은 향후 등록 경로를 확장한다.

전략 행에는 revision·정의 JSON·정의 hash를 저장하고, paper_strategy_revisions에는 버전·활성·정의·내용 hash·owner/system 출처를 추가 이력으로 남긴다. `0005_happy_machine_man.sql`은 신규 컬럼/테이블과 변경 방지/일치 트리거를 추가한다. 기존 정의 없는 행은 revision=0 기준으로 유지하며 임의 조건으로 덮어쓰지 않는다. 신규 합성 데모는 처음부터 조건을 저장한다.

## 원자적 변경과 충돌

`POST /v1/paper/strategies/:id`는 `{ expectedRevision, enabled, definition }`만 받는다. 서버에 고정된 계좌 행을 잠그고 존재하는 전략/현재 revision을 검사한다. 일치할 때만 revision 증가·현재 조건·불변 변경 이력·계좌 정지/새 epoch·감사 이벤트를 같은 트랜잭션에 저장한다. heartbeat의 계좌 version 증가 때문에 편집이 매번 충돌하지 않도록 전략 revision을 별도로 사용한다.

동일 revision의 두 저장은 하나만 커밋된다. 다른 요청은 409 PAPER_STRATEGY_REVISION_CONFLICT다. UI는 자동 재시도·마지막 값으로 덮어쓰기를 하지 않고 최신 설정으로 다시 편집하도록 안내한다. DB 오류/불확실한 응답은 저장 확인 실패로 표시하고 현재 revision을 재조회한다. 이력 저장이 실패하면 설정·정지 epoch도 롤백된다.

SQL 트리거는 현재 행의 revision 증가와 불변 ID를 검사하고 변경 이력의 update/delete/truncate를 거부한다. 커밋 시 현재 조건/최신 이력이 일치하고 계좌가 정지되어 있어야 한다. 앱은 내용 hash를 정규화된 JSON으로 계산하며, worker도 정의 hash를 다시 계산해 확인한다. 관리자에 의한 모든 우회 SQL을 완전한 공증으로 방어하지는 않는다.

## 정지와 소유권

**저장하면 활성 여부와 무관하게 모의 실행 전체가 정지**한다. 기존 worker의 epoch 검사를 무효화하고 worker가 미체결 잔량을 정리한다. 이미 체결한 현금·수량·전략별 원가는 유지한다. 종목을 바꾸어도 기존 보유분을 매도하거나 새 종목에 편입하지 않는다. 이전 종목의 자동 처리를 원하면 해당 조건을 별도로 다시 검토해야 한다.

등록 활성을 켜도 재개하지 않는다. 현재 실행기를 종료/복구한 뒤 CLI의 명시적 --resume 절차를 수행해야 한다. 활성 전략이 하나도 없으면 재개도 거부한다. 비활성 전략은 worker의 신호 계산에서 제외한다. 로그아웃은 실행 정지를 의미하지 않는다.

## worker와 주문 결합

worker는 시작 시 같은 전략 ID의 **DB 저장 정의**를 읽어 실행 입력을 구성한다. 저장 정의가 있는 전략에서는 호출자의 오래된 종목/기간/수량보다 DB 조건이 우선한다. 정의 없는 과거 행/테스트만 기존 서버 config 경로와 호환한다. UI로 저장하면 이후 DB 정의 경로를 사용한다. 실행 도중 설정이 바뀌면 자동 hot reload/재개하지 않고 정지한다.

새 주문 신호에는 구현 버전·설정 revision·정의 hash를 기록한다. 예약은 저장 정의와 hash/revision·종목·주문 수량을 다시 확인한다. 체결도 같은 binding과 최대 체결 수량을 확인한다. 활성 토글을 이용해 같은 봉 주문을 새 ID로 반복 생성하지 않도록 영구 신호 dedupe에는 설정 revision/hash를 추가하지 않는다. 기존 의도가 있는 같은 봉은 worker가 건너뛰며 직접 다른 내용으로 재기록하면 충돌이다.

합성 CLI는 저장된 활성 전략의 최대 장기 기간+1까지 필요한 봉을 요청한다(최대 2001개). 같은 과거 분의 합성 가격은 lookback과 관계없이 결정적이다. 보유한 합성 캘린더의 커버리지가 부족해 유효한 종료 봉이 모자라면 전략은 warmup으로 대기하며 미래 봉이나 가짜 종료 증거를 추가하지 않는다. 이 데모는 실제 시장 성과·휴장/유동성을 재현하지 않는다.

## 검증과 다음 단계

임시 전용 DB에서 동시 저장, 부분 체결 후 변경/정지·보유분 보존, 정의/revision/hash 위조, 체결 cap, 같은 봉 재생성 차단, 이력 변경 방지와 이력 장애 rollback을 검증한다. worker 통합 테스트는 오래된 서버 config보다 DB 정의를 사용하는지와 비활성 전략 재개 차단을 확인한다. API 테스트는 입력·계좌 주입 거부·409/불확실한 응답과 인증을 확인한다.

변경 이력은 DB에 보존하며 과거 revision 비교/복원 UI는 후속이다. [실제 시세 Paper CLI](PAPER_MARKET_SOURCE.md)는 기본 정지·전용 모의 DB·토큰 잠금 공유 방식으로 연결했다. 다음은 source 출처 강제/화면 연결, 휴장 대기·일일 기준 검토와 실데이터 운영 검증이다. 실제 주문과 외부 배포는 별도 단계다.
